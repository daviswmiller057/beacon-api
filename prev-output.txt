## Architecture and persistence

The existing path was preserved:

```text
POST /interact or CLI
→ InteractionService
→ IntentInterpreter
→ StructuredIntent
→ ActionPlanner
→ ActionExecutor
→ Beacon services
```

Context now follows:

```text
Natural language / structured intent
→ rules or Gemini interpreter
→ validated provider-neutral context intent
→ deterministic planner
→ executor
→ ContextRegistryService
→ ContextRepository
→ SQLite
```

Beacon previously had no application database. Phase 1 uses SQLite because the current deployment is a single API service and has no PostgreSQL dependencies or migration framework.

- Local default: `./data/beacon.db`
- Container path: `/data/beacon.db`
- Named volume: `beacon_data`
- Mount: `beacon_data:/data`
- Journal mode: WAL
- Foreign keys enabled
- Busy timeout: 10 seconds
- Mutations use `BEGIN IMMEDIATE` transactions

`docker compose down` removes the container and network but retains `beacon_data`. Rebuilds and forced recreation do not include or overwrite `/data`.

## Registry capabilities

Implemented:

- Entity types: person, organization, venue, location, project, routine, concept.
- Stable UUID identifiers and timestamps.
- Case-insensitive, punctuation-aware centralized normalization.
- Dotted-initial normalization such as `T.S.T.` → `tst`.
- Exact canonical-name resolution before exact active-alias resolution.
- Deterministic resolved, not-found, and ambiguous results.
- Idempotent entity, alias, fact, and relationship creation.
- Typed JSON fact values and free-form validated predicates.
- Incoming and outgoing relationship queries.
- Provenance values: `explicit_user_statement`, `system_seed`, and `model_inference`.
- Nullable source references.
- Soft deprecation for aliases, facts, and relationships.
- Explicit correction through replacement of active facts.
- Conflict rollback, including aliases that already belong to another entity.
- Safe narrowing of destructive operations only when predicate or relationship selectors identify exactly one record.
- Broad or genuinely ambiguous destructive requests modify nothing.

Natural-language writes are deterministically assigned `explicit_user_statement`, even if a model proposes another provenance.

## Documentation and limitations

The new Context Registry guide documents storage, backups, migrations, privacy, normalization, resolution, explicit learning, safe forgetting, Docker persistence, and why `docker compose down -v` deletes durable data.

Intentionally excluded:

- Passive conversation learning
- Task/calendar extraction
- Automatic entity merging
- Fuzzy matching or embeddings
- Vector databases
- Contacts or geocoding
- Context-aware scheduling
- Confidence decay
- Pattern learning
- Automatic conflict reconciliation
- GUI/dashboard work
- External integration writes

Recommended Phase 2 work is passive-learning review workflows, richer correction history and provenance weighting, context injection into scheduling, semantic retrieval where justified, and deterministic conflict-reconciliation policy.
